# Station and sensor onboarding review

**28 November 2026.** The baseline is the working tree at commit `fbe5a22883cd`, including the uncommitted sensor-driver, power-management and dashboard changes present at the start of the review. The comparison builds and browser variants ran in isolation. The three production builds used the working tree. Physical boards, installation data and cloud accounts were outside the simulation.

## Implemented results

The following measurements use the modified production sources. The historical audit and its isolated fast-sweep experiment follow this section. The operating instructions are in the [station guide](station/README.md) and the [node guide](sensor/README.md#discovery-and-re-adding-sensors).

| Scenario or resource | Before implementation | Implemented and checked |
|---|---|---|
| Older unpaired node, operator present | Four pending replies scheduled sleeps of 300, 300, 300 and 300 s | 10, 10, 10 and 300 s. An invitation starts a 45 s budget with at most three short sleeps and a ten-minute cooldown. Two missed replies within that budget still allowed the remaining short sleeps. The station window expires six minutes after an explicit operator action. |
| First contact with a sleeping node | Up to one ordinary discovery sleep before radio activity | The first wait still applies. A deep-sleeping C3 has no active receiver. The 290 s gain concerns the next opportunity to apply a saved selection after contact. |
| Two stations on one channel | An idle reply at 4 ms could prevent enrollment by the station replying at 15 ms | The 15 ms assignment won in the same exchange with one broadcast. A lone idle reply on the preferred channel takes 29 ms in the rapid-discovery fixture. |
| Two stations on different channels | A pending reply on the saved channel ended the exchange | A slow wake heard the neighbour at 4 ms and accepted the other station after 726 ms across 13 channels in the fixture. An idle neighbour alone cost 773 ms and 13 frames on a slow wake. Rapid discovery usually stops on the first channel and checks past the neighbour every fourth sequence. |
| No station available | 3,406 ms and 13 discovery frames | 3,406 ms, 13 frames and one 60-byte telemetry CRC. The 60 ms secondary search applies after a pending reply. A blind sweep keeps the ordinary response budget. |
| Incomplete saved assignment | Flags with an empty MAC could force unicast and prevent discovery | Zero, broadcast, multicast, inconsistent flags and invalid channels recovered in host tests. Independent calibration survives the repair. The normal low-power and archive exchanges require a usable unicast assignment. |
| Complete node reset | A recording clear could fail silently. Old type and calibration could be reapplied. Uptime and an old receipt could interfere with rediscovery. | The node checks the archive, recording preferences, IAQ state and configuration before acknowledging. A partial erase retries only remaining dirty sectors. Ordinary discovery advertises revision zero. A repeated matching reset receives a directed receipt on the issuing station's channel. A successful reset starts a fresh pairing window. The station offers Auto and its default interval. |
| Lost station or removal | A paired node kept addressing the missing owner. | Configuring a changing module | A BME280 selection or incompatible one-minute interval could survive a later BME688 detection | Untouched Auto stayed Auto, the interval became 300 s, and the typed name survived. | Portal or WLAN interruption | A lost token or POST response could strand a form. The tested lost replies needed one successful write. The wizard offers the home hostname and local recovery settings. A failed completion write retried after five seconds, including at timer rollover. |

| Pending-node JSON array | 1,543 bytes for one node and 29,299 bytes for 19 nodes | 154 and 2,908 bytes respectively using the review's names and telemetry. The complete compact response with 19 nodes was 2,934 bytes. Per-node history lookups fell from 19 to zero. Configured nodes also include their chosen type and interval for save readback. |

The C3 still delegates the wire CRC to ROM at `0x40000628`. The S3 uses `0x40001c98`. V4 target disassembly shows one unsigned remainder site for the initial channel rotation and none for advancing to the next channel. The baseline exchange contained two remainder sites. The radio tests covered all 169 combinations of station channel and scan rotation with no duplicate channel visit. The target compiler also removes the hourly backoff loop for the production five-minute ceiling. No hardware cycle count or battery-life estimate is inferred from the disassembly. The C3's retained boot-state structure uses 288 bytes versus 280 bytes in the original target layout. The station copies 836 bytes for a full 19-slot commissioning snapshot and releases the registry lock before serialization. Responses of at most 256 bytes use the writer's existing internal buffer. The station flash delta includes shipping both page encodings. These figures describe allocations and build sizes. The paired cold-start transfer gesture can wait until one second of application uptime with the sensor rail off. Ordinary timer wakes and the first boot of a blank node bypass that wait.

All three production targets built. The 37 C++ host suites, 16 browser suites, four upload-policy cases, eight embedded script syntax checks and both gzip round trips passed. Additional local fixtures exercised AP recovery, duplicate SSIDs, the reset and capacity lifecycle, target code generation and the production commissioning serializer. The browser suites use the embedded pages with local API doubles. The physical acceptance items include RF tail latency, charge per enrollment, GPIO9 timing, interrupted physical flash erases and native captive-browser behavior. ## Baseline from erased flash to a confirmed sensor

| Stage | What happens | What the operator can verify |
|---|---|---|
| Blank station | Install the normal `station_s3` image and partition layout. Station NVS opens, erased LittleFS is initialized and the radio starts in AP+STA mode. A nonblank filesystem that fails to mount is preserved. | The setup network is `W-Charger-XXXXXX`. The initial password is `W-Charger-Setup`. The default AP channel is 1. |
| Open the portal | Wildcard DNS resolves to `192.168.4.1`. The HTTP server redirects common Android, Apple, Microsoft and other connectivity probes. The unconfigured root and `/setup` serve the wizard. | Join the setup Wi-Fi and open [the local setup address](http://192.168.4.1/) if the OS does not launch its captive browser. |
| Choose station defaults | The seven screens cover welcome, interval, ThingSpeak, nearby sensors, home Wi-Fi, optional website password and review. The theme supports system, light and dark. The station default is 10 minutes. The custom station field takes minutes. | Sensor enrollment, the account User API Key and the website password are optional. A home SSID is required to finish. The final review shows the station interval, cloud setting, SSID and website protection. |
| Start a blank node | Install the firmware matching PCB V3 or V4. The C3 initially has no station assignment. V4 checks the battery before enabling its sensor rail. The node probes the attached module, prepares telemetry, waits a randomized 0–120 ms and broadcasts. | The station can hear a node before the sensor screen opens. Its MAC identifies the node. The I²C type describes the module on that node. One firmware image per PCB supports all ten types. |
| Add the node | The nearby-sensors page refreshes after each status request, with a one-second delay. Manual search triggers a status read. Quick-add saves name, type and interval to the station. The station leaves cloud upload disabled. | A node can also be added later in the dashboard. BME680/BME688 accept five-minute multiples. Ordinary intervals support 1–86,400 seconds. The precision presets and SW2 recording timings are sensor-specific. |
| Apply and confirm | The station sends its saved revision in a reply to the next node packet. The node persists the assignment, including station MAC and channel. A measurement-changing response requests a one-second reinitialization wake. The station clears its provisioning handshake flag on a matching, non-discovery report. | The current portal displays “already added” immediately after the station save. Node confirmation and the first valid measurement are separate milestones. The dashboard exposes requested and applied settings. |
| Join the home WLAN | Wi-Fi search is asynchronous. The scan keeps up to 20 named networks, deduplicates SSIDs using their strongest observation and supports manual entry. The optional website password is confirmed and accepts 8–64 characters. Saving schedules restart after 2.5 seconds. The AP remains available until a successful home connection. | Once connected, the station stops the AP and starts mDNS. The dashboard is available at [the station hostname](http://w-charger.local/) or its LAN IP. A previously configured station opens a recovery AP after about 30 seconds disconnected. A saved SSID routes recovery to the dashboard and Settings. |

Pending nodes can be configured in the later dashboard with type, interval, optional channel profile and supported field mappings, temperature compensation or battery calibration as applicable. Local environmental setup can skip the cloud step. TMP117, LSM6DSOX and MAX30102 use the shorter local workflow. Normal USB updates preserve settings. The station's explicit USB factory-reset target erases the whole flash. The dashboard's station reset clears station preferences and formats the station filesystem. Discovery beacons do not enter normal measurement history, and UTC history requires a valid station clock. ## Baseline discovery, deletion and replacement scenarios

| Scenario | Current behavior and timing |
|---|---|
| New node, station already on | The preferred channel is tried first. Both blank devices default to channel 1. An unpaired node tries the other channels until it receives a valid response or exhausts all 13. An unprovisioned reply can supply a preferred channel for the next wake. |
| Wizard closed partway through | Each successful quick-add already committed that sensor to the station. The station-wide interval, Wi-Fi and password are submitted separately on Finish. Reopening a fresh setup page reloads the station state and loses unsaved browser input. |
| Node starts before the station | The normal discovery sleep is 10 s in the first 10 min, then 300 s with the production configuration. Boot, module acquisition, jitter, channel waits and browser polling add time. Discovery can reuse a sensor snapshot for five minutes. It does not repeat every sensor conversion on every beacon. |
| Node has been waiting for hours | With matching defaults, hearing the station while unprovisioned still produced another 300 s sleep. If the station starts just after a beacon, and the operator adds the node just after the next beacon, the two sleep portions can total nearly 10 minutes. The first contact and the application of the selection have different deadlines. |
| Provisioned node deleted on its own station | The station clears its pairing slot, normal history and latest reading and forgets its OTA entry. Independent MAC-based names and motion references can survive. Saved recording archives have their own deletion action. The next node transmission recreates a pending entry. Receiving the deprovisioning response clears the node's station address. A sleeping environmental node with a 24-hour interval can take nearly a day to make that first contact. |
| Factory reset of the node requested | The station persists a command delivered at contact. Successful node reset clears its configuration and IAQ learning state, retains the reset acknowledgement in RTC memory and requests a one-second wake. The station retains its sensor entry. Its pending replies can restore the previous fixed type, interval and calibration. The recorder and old-uptime exceptions below affect a complete reset. |
| Node NVS erased independently | A discovery beacon from a previously confirmed node returns it to pending on the original station. The station's initial handshake guard handles discovery traffic while first provisioning is still awaiting an acknowledgement. An ordinary firmware update preserves the assignment. |
| Same station reset or router channel changed | The station STA MAC remains the same. Environmental nodes normally try it twice on the stored channel. With no MAC acknowledgement, the commissioning guard allows 12 alternative channels once. The regular path tries three other channels per report with a retained cursor. Four successful opportunities to scan three channels cover the 12 alternatives. An outage during the first guarded scan consumes that allowance. |
| Precision or gas node already paired | TMP117/LSM6DSOX/MAX30102 use an idle telemetry heartbeat of about five seconds in the live control loop, with extra samples during recording. Channel recovery takes one alternative per eligible attempt, at least five seconds apart. CCS811 keeps its heater powered and reports at its configured interval. BME680/BME688 maintain BSEC on a five-minute cadence and normally transmit at the configured reporting interval. |
| Replacement station has a different MAC | A healthy, previously paired node continues to address its old station on every channel. In the radio fixture, two normal sends and 12 recovery sends produced 14 unicasts and zero broadcasts. Replacing a dead station requires an intentional way to clear or transfer the node's assignment. Resetting the replacement station cannot deliver that operation to the node. |
| Two stations are in range | An unpaired node accepts the first valid matching response. With two normal stations replying at 4 and 15 ms on the same channel, putting the unprovisioned station first prevented the other station's accepted configuration from reaching the node in that exchange. Reversing their order provisioned the node. Repeated wins by the same station can delay enrollment. |
| Registry reaches capacity | All 19 slots admit pending or configured nodes. The twentieth registration failed and succeeded after a slot was freed. In the current dashboard the delete button is available for configured entries, so stale pending entries are awkward to remove. The gateway exposes a general drop counter. A capacity-specific message and removal of stale pending entries would make this recoverable from the list. |
| V4 battery low or unreadable | Below 2,800 mV or with an invalid reading, a blank node skips discovery and sleeps for 24 h. A paired protected node can send a bounded battery-only report on its saved channel. Configuration and OTA are deferred. Once protection is active, recovery requires a valid reading of at least 2,950 mV. V3 has no default undervoltage pause. |

Source paths for the timing and transitions are [node configuration and radio modes](sensor/src/main.cpp), [ESP-NOW transport](sensor/src/espnow_transport.cpp), [discovery sleep policy](shared/include/power_policy.h), [station registry](station/src/sensor_registry.cpp) and [Wi-Fi recovery](station/src/wifi_service.cpp). The C3 switches off its radio in deep sleep. The station's search button therefore cannot wake a sleeping node. ## Original fault reproductions and proposed corrections

| Condition | Working-tree result | Corrective change and evidence |
|---|---|---|
| Partial pairing record | A valid-layout V6 record with both assignment flags set and a zero station MAC passed the store validator. Startup chose discovery. Transport used the two flags alone and sent zero broadcasts. | Use one assignment predicate across loading, mode selection and transport. Validate a usable unicast address and channel, and retain unrelated calibration. The isolated transport correction restored 13 broadcasts in an empty scan. A valid existing assignment kept its unicast path. |
| Remote reset after long uptime | After one simulated hour, reset caused the specified one-second wake. That wake used the age of the continuous clock and scheduled a 300 s sleep because the reset had stored zero as the discovery start time. | Anchor the new discovery window to the current logical time as part of the successful reset. The same production boot path then scheduled 10 s. |
| Station entry recreated before the reset ACK | A node had completed reset revision 12. After the station entry was recreated, the node durably applied revision 2. Its next ordinary environmental packet still advertised 12. The stored override is cleared only when the incoming revision equals the old one. | Retire a superseded reset acknowledgement after a validated, durably applied normal response. Scope outstanding acknowledgements to the station that issued them. The isolated change advertised 2 in this sequence. |
| “Factory settings” with old settings or recording faults | After the reset acknowledgement, the registry still offered the old BME280 choice, 3,600 s interval, 2.0 °C offset and 1.1 battery factor in the test. In the live recorder, failed flash erase and failed recording-NVS clear produced an immediate “Ready” state. Reboot recovered a pending sample. The ordinary environmental reset path skips recorder clearing altogether. | Define the complete-reset action across the node and station entry. Reapply Auto and documented defaults for a fresh enrollment. Preserve or explicitly remove historical station archives according to that action. Propagate recorder reset errors, cover previously used recording partitions after a type change and acknowledge only a durable outcome. Fault reproduced. Full corrective transaction remains a design and hardware validation item. |
| BME688 variant read interrupted | The dispatcher recognized the common Bosch chip ID, then treated an unreadable variant register as zero. It selected BME680, which selects a different BSEC configuration. | Accept a definite low/high variant. Use the existing bounded retry budget for an unreadable or unknown variant. In the isolated driver check the failed read left the type unresolved. The next valid probe identified BME688. |
| V4 discovery uses a cached sensor snapshot | A new 3,550 mV ADC reading correctly allowed the wake. The outgoing packet reused the previous 3,700 mV value alongside the cached environmental sample. | Send the fresh protection reading whenever available. The comparison packet carried 3,550 mV with the same single ADC read and no additional sensor startup. |
| Detection changes while the operator edits | A card changed its visible label from BME280 to BME688. Clicking Add still sent fixed BME280 and 60 s. In the unknown-to-BME688 case, Auto retained an invalid 60 s choice, which the setup API rejects. | Keep Auto as the untouched default. Refresh type-dependent choices when detection changes while preserving names and explicit selections. The browser prototype submitted Auto and 300 s for both transitions and preserved the typed name. |
| First configuration request briefly fails | The initial wizard fetch silently caught the error. Two normal save attempts sent an empty token and failed. A reload could recover the token and discarded the form. | Reacquire the configuration token before a write when it is missing, with a bounded timeout and draft preservation. The browser prototype needed one additional read and succeeded on the first submission. Reconcile the station state before repeating a write whose response was lost. |
| Station save, node confirmation and home connection are conflated | Quick-add showed “already added” while the last node packet was still in setup mode. After restart, the portal polled only its old origin. A reachable recovery AP returning HTTP 200 could also trigger the dashboard transition with home Wi-Fi still disconnected. | Expose the provisioning handshake in the small status response. Show saved, confirmed and measurement state separately. Offer a home-hostname link at once and a local recovery link when the WLAN connection fails. Both distinctions were exercised in an isolated browser variant. Actual OS captive windows and mDNS require device testing. |

The module dispatcher selected all ten individual types in controlled fixtures. Automatic selection tries Bosch at `0x76` and `0x77`, then LSM6DSOX, TMP117, MAX30102, AS7341, VL53L1X and CCS811. It chooses one module. A fixed selection checks for mismatch. A missing module still allows a healthy node to advertise its identity. Explicit battery-only mode skips rail activation. The normal Bosch/Auto bus starts at 100 kHz. Confirmed TMP117 and LSM6DSOX can use 400 kHz. The CCS811 probe has a slower bus path and additional startup allowance. Retain the bounded power cycle and recovery wakes. [Dispatcher](sensor/src/environmental_sensor.cpp) · [BSEC configuration](sensor/src/bme680_driver.cpp) · [Extended sensor probes](sensor/src/extended_sensors.cpp) · [Recording reset](sensor/src/recording_store.cpp)

Two additional recovery details follow from the station source. Setup sensor-add and final-save POSTs lack a browser-side deadline, so a stalled request can leave the buttons disabled. Also, the station consumes its portal-completion event before writing the cleared flag to NVS. If that write fails, the same uninterrupted home connection does not retry it and the next boot can reopen the AP. A bounded request timeout with readback and a retried, idempotent completion write address these cases. ## Baseline measurements and isolated experiments

### First radio exchange

The host ran the production C3 transport with a 2 ms simulated MAC completion, a 4 ms application reply on the station's channel and no other replies. Each of the 13 station channels was combined with all 13 scan rotations. The experimental variant tried 60 ms response windows on a fast sweep and then the original 260 ms windows on a full fallback sweep. Times start at the transport exchange. Boot, I²C, the discovery jitter, packet loss and browser polling are separate. This comparison measures the node receiving its configuration response. The station can see the incoming packet earlier.

| Case | Current | Experimental | Effect |
|---|---:|---:|---|
| Blank pair, channel 1 | 4 ms | 4 ms | One frame in each case |
| Channel 6, scan starting at 1 | 1,314 ms | 314 ms | 1,000 ms earlier |
| Channel 13, scan starting at 1 | 3,148 ms | 748 ms | 2,400 ms earlier |
| Median across 169 channel/rotation cases | 1,576 ms | 376 ms | 76% shorter |
| 95th percentile across those cases | 3,148 ms | 748 ms | Percentile of the fixture grid |
| Station absent | 3,406 ms, 13 frames | 4,212 ms, 26 frames | 806 ms longer and twice as many frames |
| Station on channel 13 replies after 200 ms | 3,344 ms, 13 frames | 4,150 ms, 26 frames | A slow reply needs the full fallback |

The largest operator-facing improvement came from changing the sleep *after contact*. An old unpaired node with unchanged defaults scheduled **300, 300, 300, 300 s** after four consecutive pending replies. A node-side prototype with a transient “operator is adding sensors” signal scheduled **10, 10, 10, 300 s**. For a click during that short window, the next wake is up to 290 s earlier. The first encounter still depends on the original sleep schedule. The proposed station signal needs an expiry and a per-session wake budget, including behavior under intermittent reception. Keep the regular five-minute idle cadence and the V4 protection override. Evaluate the fast radio sweep separately against RF and charge measurements before enabling it.

### Station web traffic and target code

| Measure | Current | Isolated comparison |
|---|---:|---:|
| Setup HTML body | 27,202 bytes | 8,890 bytes with build-time gzip, 67.3% smaller |
| One pending BME280, serialized sensor array | 1,543 bytes | 137 bytes for seven commissioning fields |
| Nineteen pending BME280 nodes, serialized sensor array | 29,299 bytes | 2,585 bytes, 91.2% smaller |
| Per-node history metadata lookups for those 19 nodes | 19 per refresh | 0 in the commissioning projection |
| C3 `exchange` function before link relaxation | 514 bytes, two `remu` instruction sites | 514 bytes, one `remu` site with an increment-and-wrap channel loop |

The current setup query carries `setupSensors`, but the server constructs full dashboard status. The numerical comparison used the production per-node serializer and ArduinoJson, identical synthetic readings and names, and counted only the sensor array. The seven fields were MAC, name, actual type, PCB, operating mode, station provisioning and node confirmation. Adding last-contact age or fault details would change the size. A dedicated registry snapshot could also avoid copying full views. The existing dashboard gzip negotiation can serve as the implementation pattern while retaining a plain response for clients that need one. Keeping both setup bodies costs about 8.9 kB of additional flash. [Status handler](station/src/web_portal.cpp) · [Embedded pages](station/src/web_pages.cpp) · [Existing gzip generator](station/dashboard_gzip.py)

The C3 disassembly shows the compact CRC wrapper jumping to ROM `crc32_le` at `0x40000628`. The S3 linker map and disassembly resolve the corresponding call to `0x40001c98`. A 13-channel environmental discovery computed the CRC once over 60 bytes in the production transport test. Live frames that refresh acquisition ages can require another CRC. The 80 MHz C3 already uses hardware integer remainder for the scan. The increment-and-wrap experiment preserved all 169 preferred-channel/start combinations and the unchanged baseline function bytes matched the PlatformIO object. No MCU-cycle, current or wall-clock gain was measured for this instruction substitution. The S3 already prepares its reply from RAM and queues storage work separately. These paths have lower priority than a wrong provisioning state or another 300 s sleep. ## Original validation and implementation order

- **Production builds passed.** Station S3 used 1,665,826 bytes of application flash and 78,764 bytes of static RAM. Sensor V3 used 1,100,007 and 45,116 bytes respectively. V4 used 1,100,879 and 45,116 bytes. The builds performed no uploads.
- **All 37 production host suites passed**, along with four station upload-policy checks and syntax checks for eight embedded scripts. Focused host experiments exercised the Wi-Fi service, node boot, config store, module dispatch, radio, registry and recording fault sequences described above.
- **Browser coverage used the actual embedded pages and local API fixtures.** Seven portal scenarios ran against both the baseline and the prototype. A separate dashboard scenario added, confirmed, deleted, rediscovered, added again and queued a node reset. The existing sensor-settings, ThingSpeak and 19-node interaction-stress browser suites passed.
- **Two existing browser suites failed on this working tree and passed against the unmodified commit.** The compact-dashboard check measured a 10 px gap at 390 px viewport width after settling, against its 16 px minimum. The UI-reliability check found the expected environmental-read-failure text in a hidden element. Restore the detail-view spacing and verify a visible failed-reading indication with the current presentation. [Compact dashboard check](tests/test_compact_dashboard.cjs) · [UI reliability check](tests/test_ui_reliability.cjs)

Implement the durable reset and common assignment validation first, together with reliable type detection and an honest node-confirmation indicator. Next address the setup form, the AP-to-LAN handoff and the compact status response. A bounded assisted-enrollment window then has a reliable confirmation path to shorten. A deliberate transfer procedure can cover replacement stations without disrupting paired nodes during ordinary outages.

For physical acceptance, timestamp first node power, first station receipt, first visible card, station save, node acknowledgement and first valid reading separately. Compare a cold node and a node already in the five-minute cadence on both PCB revisions. Exercise channel 1 and a late scan channel, an AP-to-router transition, poor reception, a simultaneous Wi-Fi scan and multiple nodes. Record p50/p95, missed acknowledgements, frame counts and charge per successful enrollment as well as the station-absent cost. Use regular images for charge and separate instrumented runs for timing. Physical RF, captive mini-browser behavior, rail or current measurements and interrupted flash erases remain unmeasured in this review.
